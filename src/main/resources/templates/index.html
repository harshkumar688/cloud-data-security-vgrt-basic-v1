SECURITY ANALYSIS & MOTIVATION

The Cloud Dilemma & The V-GRT Solution

Understanding why traditional multi-tenant storage architectures fail and how V-GRT establishes provable cryptographic protection.

THE CONVENTIONAL PROBLEM
Vulnerability Vectors

Traditional Multi-Tenant Cloud Exposure

In standard cloud systems, tenant isolation relies purely on loose database flags. Storage servers hold unencrypted files or shared encryption keys accessible to platform operators and malicious insiders.

  • Plaintext File Storage: Files stored unencrypted on disk are vulnerable to direct host compromise.
  • Shared Encryption Keys: Global server keys expose all users if a single administrative leak occurs.
  • Untracked Data Access: Inadequate or mutable audit logs prevent forensic security analysis.
  • Silent Bit Rot / Tampering: Downloaded files lack mathematical integrity validation.
THE ARCHITECTURAL SOLUTION
V-GRT Enforced

The V-GRT Engineered Paradigm

V-GRT enforces a Zero-Plaintext architectural boundary. Every stored file is sealed with an ephemeral symmetric key wrapped asymmetrically, combined with database-level isolation and tamper-evident audit trails.

  • Zero-Plaintext Persistence: Only AES-256-GCM ciphertext bytes are ever written to the physical storage disk.
  • Hybrid Envelope Encryption: Fresh 256-bit AES key per file, wrapped with RSA-OAEP-2048 public key.
  • Cryptographic Digest Integrity: SHA-256 hash verified during download before bytes reach the client.
  • Immutable Security Ledger: Detailed chronological audit trail recording all logins, transfers, and access denials.

DATA FLOW SPECIFICATION

How It Works: The Ingestion & Retrieval Pipeline

Step-by-step cryptographic sequence executed on every file upload and download.

01

Client Upload & Validation

Client submits file via CSRF-protected HTTPS multipart request. File size is checked against the 10 MB boundary, and path traversal characters are sanitized.

Input Filter
02

AES-256-GCM Symmetric Sealing

A cryptographically strong 256-bit key and 12-byte initialization vector (nonce) are generated in RAM. The file payload is encrypted into ciphertext with a 128-bit authentication tag.

AES-256-GCM
03

Asymmetric RSA-OAEP Key Wrapping

The ephemeral 256-bit AES key is encapsulated using the platform's 2048-bit RSA public key with Optimal Asymmetric Encryption Padding (OAEP with SHA-256 and MGF1).

RSA-OAEP-2048
04

Zero-Plaintext Storage & Audit Recording

Only encrypted ciphertext bytes are written to disk under a randomized UUID. Plaintext bytes and raw AES keys are purged from memory. An audit event is committed.

Zero Plaintext
05

Verified Retrieval & Integrity Validation

On download request, ownership is checked. The private RSA key unwraps the AES key, the ciphertext is decrypted, and the calculated SHA-256 digest is verified before streaming.

SHA-256 Verified

TOPOLOGY SPECIFICATION

Security Architecture Preview

Conceptual separation of concerns between client traffic, virtualization boundary, cryptographic core, and storage.

BOUNDARY 1
Client Ingestion Layer

HTTPS / TLS 1.3 encrypted browser communication. CSRF validation tokens and file size boundary enforcement.

BOUNDARY 2
Virtual Tenant Scoping

Spring Security context enforces account ownership. Repositories query exclusively by authenticated username.

BOUNDARY 3
Crypto Orchestrator

`CryptoService` generates fresh 256-bit keys, encrypts payloads, and wraps keys using public RSA-OAEP certificates.

BOUNDARY 4
Ciphertext Vault & DB

Protected filesystem contains only `.bin` ciphertext files. JPA database stores only wrapped keys and metadata.

BOUNDARY 5
Immutable Audit Ledger

Dedicated `AuditEventRepository` writes immutable records of successful and denied operations for admin governance.

COMPONENT SEQUENCE & CONNECTIVITY

Data & Control Flow Connections

Linear Execution Chain

The V-GRT architecture enforces a strict 10-stage sequential flow. Every operation—whether a file upload, inspection, or download—must traverse this deterministic path to guarantee end-to-end security:

01

Client / User Layer

Connection: The user accesses the web client over TLS 1.3. Browser sessions initiate HTTP POST/GET requests carrying session cookies or credential payloads. Zero sensitive cryptography is entrusted to vulnerable client JavaScript; all critical cryptographic operations are executed in secure server enclave memory.

Implemented
02

Authentication Engine

Connection: Intercepts client credentials via Spring Security DaoAuthenticationProvider. Passwords are verified against stored BCrypt hashes (work factor 12). Successful authentication issues an HTTP session token; failed attempts immediately trigger security event logging.

Implemented
03

Authorization & RBAC

Connection: Evaluates the authenticated principal against Spring Security SecurityFilterChain rules. Distinguishes standard tenant roles (ROLE_USER) from administrative governance roles (ROLE_ADMIN). Unauthenticated or unauthorized requests are rejected at the servlet filter boundary before controller execution.

Implemented
04

Tenant Isolation (Virtualization)

Connection: Enforces logical compartmentation in the data tier. The authenticated username is injected into repository query parameters. Database operations are strictly constrained such that User A cannot read, modify, or infer the existence of User B's files.

Implemented
05

Hybrid Envelope Encryption

Connection: The uploaded byte stream is consumed by the CryptoService. An ephemeral 256-bit symmetric key is generated via SecureRandom. File bytes are encrypted into ciphertext using AES-256-GCM (with a 12-byte IV and 128-bit authentication tag). The AES key is wrapped via RSA-OAEP-2048 before committing to persistence.

Implemented
06

Private Encrypted Storage

Connection: Encrypted file payloads, wrapped symmetric keys, initialization vectors, and metadata are persisted in the isolated database layer. At no point are unencrypted file bytes written to disk or stored in secondary storage tables.

Implemented
07

Integrity Verification Engine

Connection: During retrieval, the RSA private key unwraps the AES data key, and AES-256-GCM decrypts the payload. The plaintext byte stream is immediately hashed via SHA-256 and compared against the original upload checksum. Any discrepancy halts the stream and registers a critical integrity breach alert.

Implemented
08

Risk Engine (Threat & Anomaly Evaluation)

Connection: Continuous telemetry ingestion point. While current code implements deterministic failure logging and checksum anomaly traps, the planned automated Risk Engine will aggregate access velocity, geolocational divergence, and brute-force indicators into an automated risk score to throttle suspect sessions.

Proposed Roadmap
09

Forensic Audit Ledger

Connection: Every lifecycle transition—successful authentication, failed password attempts, file upload encryption, and integrity-verified downloads—synchronously records an immutable event in the audit database table with user identity, client IP, action type, and UTC timestamps.

Implemented
10

Unified Security Dashboard

Connection: Visualization tier. Currently administrators review operational telemetry through the raw tabular Audit Ledger (/admin/audit). The planned Security Dashboard will present time-series charts, tenant threat heatmaps, and encryption throughput graphs.
